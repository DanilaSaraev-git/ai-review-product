# Синтетические ТЗ с внесёнными ошибками

Назначение: контрольный набор для настройки и оценки ревью. Каждое ТЗ существует в двух версиях — с внесёнными ошибками и без них. Тестовые данные кейсодателя уже использованы при подготовке базы и настройке PoC, поэтому независимым контролем они быть не могут ([прогоны PoC](../poc-review-data-spec/README.md)). Этот набор закрывает пробел: ошибки в нём известны заранее и перечислены ниже.

Статус: **синтетический материал, экспертная оценка не проводилась**. Набор не доказывает качество модели и не является разметкой реальных ошибок MTS. Частота и стоимость этих ошибок в реальной документации не измерены.

## Как построен набор

Структура разделов взята из шаблона «Потоковые данные/витрины» ([Шаблоны документации.pdf](../../Шаблоны%20документации.pdf)). Ошибки внесены двух видов:

- **Нарушение обязательного требования** — 8 пунктов из [Основные моменты документации.pdf](../../Основные%20моменты%20документации.pdf): спецификация сериализации, ссылка на Дата-каталог, признак NOT NULL/NULLABLE, типовые фильтры, сохранение всех разделов шаблона с пометкой «не применимо», кластер Kafka, полный путь в HDFS с форматом, перечень справочников.
- **Неоднозначность** — по образцам наблюдений M-01…M-09 из [первичного разбора примеров](../../document-analysis.md): неизмеримая задержка, нераскрытый список полей, неопределённая семантика времени, фильтр без поля и порядка, ссылка на отсутствующее поле, противоречивый порядок fallback, отсутствие правил при равенстве, конфликт инкремента и полной перезагрузки, мера в списке ключей группировки.

Домены документов выбраны отличными от примеров кейсодателя (события QoS и витрина утилизации сот вместо геолокации, CDR и агрегата по устройствам), чтобы набор не воспроизводил уже разобранные тексты.

## Правила чистых версий

- Чистая версия — контроль на ложные срабатывания: в ней устранены не только внесённые ошибки, но и всё, что дало бы обоснованное замечание по тем же правилам. Ожидаемый результат ревью на чистой версии — отсутствие замечаний по перечисленным ниже пунктам.
- Заглушки вида `TOPIC_QOS_CENTRAL`, `USER_A`, `LINK_DATACATALOG_...`, `CLUSTER_HADOOP_NET_PROD` сохранены в обеих версиях. По [решению D-13](../../../knowledge/decisions.md) заглушки трактуются как реальные данные, поэтому их наличие ошибкой не считается; ошибкой считается отсутствие самого элемента (например, строки со ссылкой на Дата-каталог), а не то, что вместо адреса стоит заглушка.
- Кроме перечисленных ошибок версии совпадают по составу разделов, полям и цифрам. Различия в разделе «История изменений» отражают правку и не являются частью набора.

## Как использовать

1. Подать версию с ошибками на вход ревью и сопоставить полученные замечания с реестром: какие ID найдены, какие пропущены.
2. Подать чистую версию и посчитать замечания, не относящиеся ни к одному ID, — это оценка ложных срабатываний.
3. Обсудить с экспертом кейсодателя, какие из внесённых ошибок он считает реалистичными и какие встречаются чаще; до такой проверки набор остаётся нашим предположением о типичных ошибках, а не измеренным распределением.

Ограничение переносимости: обязательные требования взяты из материалов MTS и подтверждены только для этого кейса ([D-13](../../../knowledge/decisions.md)). Для других компаний перечень обязательных элементов проверяется отдельно.
